What building an LLM contract-extraction pipeline taught me about evaluation: ten ways my eval lied, and why the model was rarely the problem.
Author

Santosh Kumar Panda

Published

October 12, 2026

The first time I scored my contract extractor, it got zero out of six fields right on the first contract.

Every one of the six was correct.

The model had done its job. My scorer hadn’t. That moment set the theme for the whole project: when you build with LLMs, the evaluation is code too, and a wrong eval is worse than no eval, because it sends you off “fixing” a prompt that isn’t broken.

This post covers what I built, the ten ways my eval lied to me, what the real numbers looked like once it stopped lying, and why most failures weren’t the model’s fault. You can explore every failure yourself further down.

The setup

The task: take messy commercial contracts in, and return clean, structured JSON records out, with quality measured per field.

I used CUAD, a public set of commercial contracts from SEC filings, labelled by legal experts. Having labels from day one meant I could measure from the start instead of eyeballing outputs.

I picked six fields that cover different types, because each type needs its own way of deciding “is this right?”:

Field Type What makes it hard
Parties List of entities Aliases (“MBE”, “the Company”), partial matches
Agreement date Date Formats, blanks like “March ___, 1999”
Governing law Jurisdiction “Ontario” vs “Ontario, Canada”
Renewal term Duration “twelve (12) months each” vs “successive 1 year”
Cap on liability Yes / no The definition is broader than it sounds
Non-compete Yes / no Overlaps with exclusivity clauses

The pipeline is deliberately simple:

Docling turns each PDF into markdown. A Pydantic model defines the record, and OpenAI’s structured outputs constrain the model’s response to that schema, so I always get valid, typed JSON back. Three schema choices did most of the work:

  • Absence is explicit. Fields are str | None with no default, so the model has to decide “present or not” every time instead of skipping the field.
  • Every value comes with evidence. A verbatim quote from the contract, which I can check is really in the source.
  • The field descriptions are the prompt. The model reads them, so I wrote them like instructions to a junior paralegal.

One thing to be clear about: structured outputs guarantee the shape of the answer, not its truth. A perfectly valid record can still hold the wrong date. That’s what the evaluation is for.

Ten ways my eval lied

Here’s the full list. Every one of these produced output that looked plausible, which is exactly what made them dangerous.

  1. I compared against the wrong column. CUAD has a raw clause-text column and a normalised answer column for each field. I scored against the raw text, so “Delaware” never matched a full sentence about Delaware law.
  2. I used exact string equality for every field. “2007-04-06” doesn’t equal “April 6, 2007”.
  3. “Absent” had five spellings. None, NaN, "", [] and False all mean “not in the contract”, but they didn’t compare equal to each other, so correct absences were marked wrong.
  4. A column lookup silently missed. I searched for a column starting with “party”. The column is called “Parties”. The ground truth for parties was empty for all twenty contracts.
  5. True negatives counted as hits. When both the model and the label said “no”, my code counted a true positive. That inflated recall on the two yes/no fields.
  6. Wrong values only counted as misses. If the model said Illinois and the label said New York, I counted a false negative but not a false positive, so precision showed a perfect 1.00 alongside three wrong answers.
  7. The join between outputs and labels was a substring match. A filename ending “…Agreement” could match one ending “…Agreement3” and score a contract against another contract’s labels.
  8. Contracts were dropped silently. A continue skipped contracts while the header still said “20 contracts”.
  9. My name cleaning merged entities. Stripping everything in brackets turned “TOM Online (BVI) Limited” into “tom online limited”.
  10. I read a stale results file. An old output got re-shared as new. The numbers looked familiar because they were the old ones.

The fixes are boring, and that’s the point. One matcher per field type. One function that decides what “absent” means. An explicit map from field to column that raises an error if a column is missing. Exact joins. A check that every field’s outcomes add up to the number of contracts scored. And unit tests built from the awkward real values I’d just been burned by.

What I measure now

True negatives appear in neither formula on purpose. If a clause is missing from 80% of contracts, a model that always says “not present” scores 80% accuracy and zero recall. Accuracy would make it look good; recall tells the truth.

The core of the scorer is small:

def classify(ext, truth, matches=exact) -> list[str]:
    ext_present, truth_present = not is_absent(ext), not is_absent(truth)
    if not ext_present and not truth_present: return ["TN"]
    if ext_present and not truth_present:     return ["FP"]
    if truth_present and not ext_present:     return ["FN"]
    return ["TP"] if matches(ext, truth) else ["FP", "FN"]

The real baseline

With the scorer fixed, here’s the first honest run on 20 contracts. Parties is scored per party, so its counts don’t add up to 20. Support is how many real examples each recall figure rests on.

Field TP FP FN TN Support Precision Recall
agreement_date 18 2 1 0 19 0.90 0.95
governing_law 18 1 1 1 19 0.95 0.95
cap_on_liability 4 0 14 2 18 1.00 0.22
non_compete 4 1 8 7 12 0.80 0.33
parties 44 1 47 0 91 0.98 0.48
renewal_term 1 12 10 7 11 0.08 0.09

The pattern is clear: precision is high almost everywhere. When the model gives an answer, it’s usually right. It fails by not answering, or by answering in a different shape from the label.

NoteSmall samples are noisy

Non-compete recall of 4 out of 12 has a 95% confidence interval of roughly 0.14 to 0.61. One more hit would move it by eight points. Always report the support next to the number.

Blame the model last

When I sorted the failures by cause, the picture changed completely:

  • Definition (41): my field description didn’t match what the labellers meant. Cap on liability is the big one: I asked for a monetary cap, and the labellers clearly counted more than that. For parties, the labels include defined short names like “MBE” and even boilerplate like “each a Party”, while I asked for legal names only.
  • Schema (10): the model found the right clause and returned it in the wrong shape. Nine of the ten renewal-term misses are a full sentence where the label says “successive 1 year”.
  • Label noise (2): one contract is clearly dated but has an empty date label; another has expiry dates where a duration should be.
  • Model (3): an invented day for a blank date, an initial term returned as a renewal term, and one debatable extension clause.

Three genuine model errors out of 56. The rest were me: my scorer, my schema and my definitions. The order I now check failures in is loader, matcher, schema, label noise, and only then the model.

What I’d do next

  • Rewrite the cap-on-liability and non-compete descriptions from what the labellers actually marked, then rerun on the same 20 contracts and compare. One change, one rerun.
  • Restructure renewal term into a length, a unit and a “successive” flag, so “twelve months each” and “successive 1 year” compare equal.
  • Decide what a party is, and either extract aliases too or filter them out of the labels, with the rule written down.
  • Set aside a held-out test set before tuning anything, sampled across contract types. My 20-contract sample was mostly one type of agreement, which is its own lesson.

Takeaways

  1. Your eval is code. Test it, make it check itself, and distrust any number you haven’t traced back to a raw value.
  2. Definitions beat prompts. Most of my “model errors” were disagreements about what a field means.
  3. Precision and recall per field, with support. One accuracy number would have hidden everything in this post.
